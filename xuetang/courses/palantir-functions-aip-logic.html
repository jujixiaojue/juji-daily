Palantir Functions 与 AIP Logic：代码函数和逻辑函数怎么分工

Foundry 里的 Functions 是用 TypeScript 或 Python 写的、在隔离环境里服务端执行的代码逻辑；AIP Logic 是无代码环境，用来编排可被平台当函数调用的「逻辑函数」。两者都能读本体，也能准备编辑，但真正改对象必须经过 Action。另外还有只读的 Query，以及用 SQL 定义的 Ontology SQL functions，不要和前两者混成一种东西。

1. 导读与辨名

同事口头里说的「Palantir 的 function 和 logic」，在官方文档里并不是一对对称的产品名。需要先把名字对齐，后面的分工才说得清。

官方文档把代码侧叫作 Functions。它指的是：由代码作者编写、在服务端隔离环境中快速执行的逻辑，并且原生支持按 Ontology（本体）来读属性、遍历链接、准备编辑。在对象上读写的那一类，文档又称为 functions on objects（FoO，对象上的函数）。在 Slate 里，为了和文档内部那套 JavaScript 片段区分，Functions 产品也被叫作 Foundry functions。本课没有找到名为「Foundry Logic」的独立产品页；人们说的 Logic，对应的官方产品名是 AIP Logic，它产出的是 Logic function（逻辑函数）。

AIP Logic 的官方定位是：一个无代码开发环境，用来创建、测试和部署「由 AI 驱动的函数」，让你用点选方式调用大语言模型（LLM），并接上本体里的数据。逻辑函数在平台里可以像普通 FoO 一样被调用，例如用在 Workshop 模块中。

表 1　先辨名：本课涉及的官方名称（据第 1 节所引文档整理）

2. Functions：代码函数怎么工作

官方概述的原话大意是：Functions 让代码作者编写能在运营场景（如支撑决策的仪表盘和应用）中快速执行的逻辑；这段逻辑在服务端的隔离环境中运行。它原生支持按本体编写逻辑，包括读取各类对象类型的属性、遍历链接，以及灵活地准备本体编辑。

文档列出的常见用途包括：为 Workshop 返回对象集或变量值；用 function-backed columns 在表格里显示变换后的值；为 Workshop 图表做聚合；通过 function-backed action 表达一次更新许多对象的复杂编辑；在 Slate 后端计算后交给前端展示；在 Quiver 里算自定义指标或聚合；用 external functions 查询外部系统以丰富对象；在与语言模型协作时流式返回结果；以及把 Python 函数当作 Pipeline Builder 里的 sidecar 容器。

语言、仓库与发布

目前支持的语言是 TypeScript 和 Python，具体分为 TypeScript v1、TypeScript v2 和 Python。三种语言都能完成运行、测试和发布这些基本平台能力，但高级特性并不对齐。文档建议大多数新工作流优先考虑 TypeScript v2，以获得完整 Node.js 运行时、一等的 Ontology SDK（OSDK）支持、可配置的资源请求，以及测试版的 staged writes（暂存写入）。Python 与 TypeScript v2 都支持 OSDK。

工作流程可以概括为：在项目中新建 Functions 仓库（或从 Code Repositories 新建）并选定语言 → 在 VS Code workspace（文档推荐）或网页版 Code Repositories 里编写 → 用 Live Preview 试跑 → 提交到仓库的 master 分支并 Tag version，把仓库里的函数发布到 functions registry → 再在 Workshop、Action、Slate 等处按已发布版本调用。Live Preview 的运行时与已发布函数并不相同，文档写明差别包括 CPU、内存和超时。

任何要在函数里使用的对象类型、接口或链接类型，必须先导入到仓库所在的 Project。导入发生在 Project 级别，改一个仓库的 Ontology 导入可能影响同一 Project 里的其他仓库。

在平台里怎么被消费

Workshop 里，多数变量可以由函数计算；函数结果会按相同输入做缓存，也可配置重算行为。Object Table 可以有函数支撑的派生列，用户滚动时即时重算。Chart 可以使用函数支撑的聚合。Slate 在 Platform 页签里添加 Foundry Function，并可与 Slate 自己的文档内 functions 组合使用。Quiver 的对象集图与 Workshop 图表共用底层组件，也支持函数支撑的聚合，以及带对象参数的 code function 卡片。Automate 可以在条件满足时自动执行函数：对稳定版本（1.0.0 及以上）可打开兼容版本自动升级；在 Automate 里函数异步执行，最长可达 4 小时。注意：作为 Automate 的 Function effect 时，返回本体编辑的函数不会把编辑真正写进去，详见第 5 节。

3. AIP Logic：逻辑函数怎么工作

一条 Logic function 接收本体对象或文本等输入，返回值（例如字符串）、对象，或对本体的编辑。它由 blocks（块）组成。块可以读或写本体、做计算与聚合、调用其他函数、遍历集合、判断条件，或与 LLM 交互。把块串起来，前一块的输出就成为后一块的输入。

使用入口是工作区导航或快捷键（macOS 为 CMD + J，Windows 为 CTRL + J），也可以在 Files 里选 +New → AIP Logic。逻辑文件必须保存在项目文件夹中，不能放在个人主文件夹。界面从左到右主要是：输入 / 块 / 输出的配置区、Debugger、Run 面板。右侧还有与 Automate、AIP Evals 的集成。

支持的输入类型包括 array、boolean、date、double、float、integer、long、media reference、model、object、object list、object set、short、string、struct 和 timestamp。最后一块的输出就是整条逻辑函数的输出，可以是值（原始类型或对象），也可以是该函数做出的全部本体编辑。

常用块与工具

官方介绍的常用块包括：

  • Use LLM：AIP Logic 的核心。由提示词（prompt）、工具（tools）和输出组成，可选用平台上已提供的 LLM。文档把工具分成 data、logic、action 三类。LLM 不能直接使用工具，只能提出工具调用请求，再由 AIP Logic 在调用者权限范围内执行。
  • Apply action：不经过 LLM，确定性地调用 Action，参数由你填，执行更快。
  • Execute function：调用已有的 TypeScript、Python 函数，或其他逻辑函数，避免把已有逻辑再写一遍。
  • Conditionals：按条件走不同路径。各分支的输出类型必须一致；若分支通过 Action 返回本体编辑，其他分支必须同样执行 Action，或显式选择 “take no action”。
  • Loops：遍历集合，对每个元素做变换或执行 Action。循环只接受 List，不接受 Array；若输入是 Array，会自动先插入 “Array to List” 块。若循环内没有 Action，各次迭代会并行执行。
  • Create variable：创建供后续块使用的变量。

Use LLM 块可用的工具包括：Apply actions（让 LLM 经 Action 编辑本体）、Call function（让 LLM 调用代码函数或已有逻辑函数）、Query objects（指定对象类型及可见属性，供 LLM 查询）、以及 Calculator tool（做准确的数学计算）。Query objects 应只勾选必要属性，以节省 token。

跑一次逻辑函数会打开 Debugger，展示各块里 LLM 的思维链（chain-of-thought）以及用到的工具，便于排错。发布之后可以用 AIP Evals 写详细测试，比较模型、观察多次运行的方差，并用 AI FDE 根据失败用例分析提示词。执行模式有两种：默认的 user-scoped（按运行者本人权限执行，每人只能看自己的执行日志，日志保留 24 小时）和 project-scoped（按逻辑函数所在项目的权限执行，项目成员可见日志；所用资源必须导入同一项目，用户还需具备这些资源的 marking 权限。此模式还可把运行历史写入数据集，保留最近 10000 次）。

逻辑函数的用法，官方写明可以像普通 FoO 一样：用逻辑函数支撑 Action，再从 Workshop 调用；用逻辑函数支撑 Workshop 的 Markdown 控件（此时输出类型必须是字符串）；在其他逻辑函数里调用它；也可以在对象上的函数里调用它。Uses 页签可以复制一条 curl，在 Foundry 外的终端运行，但返回本体编辑的逻辑函数没有这条路径。

4. 两者如何配合

可以把 Functions 理解成「用代码写死、可测试的确定性能力」，把 AIP Logic 理解成「用块编排、常常带着 LLM 判断的函数」。它们不是互斥产品：逻辑函数在平台里按函数来消费，并且可以调用代码函数；代码函数也可以调用逻辑函数。

官方给出的典型接法是：把已经写好的确定性能力（例如语义检索函数）放到 Execute function 块里直接调用；若希望由模型决定何时调用，就在 Use LLM 块里挂上 Call function 工具。反过来，语义搜索这类工作流也可以「先写一个 function-on-object，再从 AIP Logic 调用它」。FAQ 还建议：能用确定性块（transform、execute、apply action）就不要交给 LLM，这些块不消耗 token，结果也更可预期。

5. 改本体必须经过 Action

这是最容易踩错的一点。官方在 Ontology edits 文档里写明：一个常见误解是「运行编辑函数就会更新本体里的对象」。在 Authoring 的 functions helper 里运行 Ontology edit function，不会把编辑应用到真实对象。要用函数更新对象，必须把该函数配置到一个 Action 上，也就是 function-backed action。

AIP Logic 同样如此。在 Logic 里运行函数时，Debugger 的 scenario 会显示所有拟定的本体编辑，但这些编辑此时还不会真正执行。若要写入本体，需要：把已发布的逻辑函数从 Action 调用，或从 Automate 调用。即便逻辑里已经放了 Apply action 块，官方也写了：必须从 Action 调用这条逻辑函数，编辑才会写回本体；「即使函数里包含 Apply action 块，只要不是从 Action 执行，本体也不会被修改」。

为了让逻辑函数能够编辑本体，入门文档给出的步骤是：在 Use LLM 块中配置 Apply actions 工具 → 迭代完成后 Publish → 再创建一个由该已发布逻辑函数支撑的新 Action → 在 Workshop 模块里使用这个 Action。文档在核心概念里也概括为：要编辑本体，逻辑函数必须先发布，再从 Action 调用。

Automate 这边要再分清两种 effect：

  • Function effect：不会应用函数返回的本体编辑。若自动化需要写本体，应配置 function-backed action，再用 Action effect。
  • Logic effect：可以自动运行 AIP Logic 函数，但只能调用「输出为本体编辑列表」的逻辑函数。若逻辑函数启用了 staged writes，它不再返回本体编辑列表，在选择器里会显示为不可用；这时要先用 AIP Logic Usage 页的 Create action（或在 Ontology Manager 里为该函数创建 Action），再改用 Action effect。文档也提到，可以关闭 staged writes 以回到旧行为；给一条原本返回编辑列表的逻辑函数打开 staged writes，会发布新的主版本，因为输出类型变了。

经 API gateway 对外时，分工也很明确：Query 是只读子集，不能修改本体或外部系统；需要编辑能力时应使用 Action。

7. 典型例子（均来自官方示例）

以下代码和提示词均改写自官方文档中的示例或示意（notional）材料，只为说明机制；对象类型名称以文档为准，不是某家租户里的真实模型。不要直接复制到未导入相应对象类型的仓库里运行。

示例 A：对象上的只读函数（Functions on objects）

官方入门用 Airport 对象，把 city 和 country 拼成可读的地点字符串。这是最典型的 FoO：输入是一个对象，输出是给 Workshop 变量或界面使用的值。下面保留 TypeScript v1 原文结构。

import { Function } from "@foundry/functions-api";
import { Airport } from "@foundry/ontology-api";

export class MyFunctions {
  @Function()
  public airportLocation(airport: Airport): string {
    return `${airport.city}, ${airport.country}`;
  }
}

出处：Getting started with functions on objects。同一页还给出了 TypeScript v2 的等价写法（默认导出，类型为 Osdk.Instance<Airport>）。

示例 B：准备链接编辑的函数（仍须经由 Action 才写入）

官方 Ontology edits 页用员工与工单的多对多链接 assignedTickets：为一名 Employee 增加一张工单链接、并移除另一张。函数返回的是编辑，而不是立刻改库。

import { Edits, OntologyEditFunction } from "@foundry/functions-api";
import { Employee, Ticket } from "@foundry/ontology-api";

export class TicketLinkFunctions {
  @Edits(Employee, Ticket)
  @OntologyEditFunction()
  public reassignTicket(
    employee: Employee,
    ticketToAssign: Ticket,
    ticketToUnassign: Ticket
  ): void {
    employee.assignedTickets.add(ticketToAssign);
    employee.assignedTickets.remove(ticketToUnassign);
  }
}

出处：Ontology edits。该页同时给出 TypeScript v2（createEditBatch）和 Python（FoundryClient().ontology.edits()）写法。

示例 C：AIP Logic 的示意提示词，以及调用已有函数

Blocks 文档里有一段示意提示词：让模型只看投诉邮件正文，寻找类似历史邮件，并只返回一条过往有效的解决方案，而不是罗列每封邮件的发现。

官方示意提示词大意是：You are my complaint helper agent. Find other emails that describe similar events to those described in the input email. Look only at the email body. Determine the best solution based on what has worked in the past. Return your one solution recommendation, do not list findings from every email.

同一页的 Execute function 示例则是：先调用一个语义搜索函数，再借助相似事件返回处理说明文本。这正是第 4 节说的「确定性检索放在代码函数里，Logic 负责编排」。Apply action 块的示例则是：给某个 incident 赋予优先级，且不经过 LLM，以保证参数填写是确定的。出处：AIP Logic · Blocks。

示例 D：Ontology SQL function（另一种「函数」）

若需求只是「按参数查出一类对象」，官方给出的是在 SQL Studio Object mode 里发布一条参数化 SQL，而不是新建 TypeScript 仓库。参数只能是字面量，不能是一段 SQL 片段；ObjectSet 参数只能出现在 FROM 子句。

DECLARE @animalParam STRING = 'dog';

SELECT *
FROM `ri.ontology.main.object-type...`
WHERE animaltype = @animalParam;

出处：Ontology SQL functions。发布后它会像其他本体函数一样出现在 Workshop、Actions、Automate 和 OSDK 里，但仍然是只读的。

8. 常见坑与已公布限制

  • 编辑函数「跑通了」不等于已经改库。functions helper、Logic Debugger 里看到的是拟定编辑。没有经 Action（或符合条件的 Automate Logic / Action effect）就不会写入。见第 5 节。
  • 超时在预览环境和生产调用里不一样。Functions 默认运行时限 60 秒，可在函数配置页修改；Live Preview 允许跑到 280 秒，即使配置页改过也如此。Automate 中的函数异步执行最长 4 小时。TypeScript v1 另外还有不可配置的 30 秒 CPU 时间上限。AIP Logic 在 Debugger 里测试时不受五分钟执行时限约束，但从 Workshop 或函数执行 API 调用时会执行该五分钟上限——这是 FAQ 里「调试能过、Workshop / API 失败」的常见原因。
  • 内存与对象加载。TypeScript v1 内存上限 128 MB，且一次 .all() / .allAsync() 不能加载超过 100,000 个对象，也不能一次使用超过 3 次 search around；文档还提示，即使是数万对象也常会先撞上时间或内存上限，这时应改用聚合，或排序后取子集。Serverless 的 Python 与 TypeScript v2 默认内存 1024 MiB，可在 512–5120 MiB 配置。已部署的 Python 函数默认 2 GB，且文档写明目前不能在配置页调整内存。
  • 刚编辑完立刻搜索，可能仍看到旧值。对对象和链接的修改，要等函数执行结束后才传播到对象集 API。因此，依赖被编辑值的 Objects.search()（过滤、search around、聚合）仍会使用旧数据。按主键取回你已经编辑过的那个对象则不同：基础设施会在物化时套用未提交编辑。若要在同一次函数里「先改再搜」，必须自己处理这种滞后。官方示例把某位员工改名为 Bob 后再按新名计数，期望为 1，实际为 0。
  • 可选数组在 Action 里会变成空数组。在代码仓库里跑 @OntologyEditFunction 时，被省略的可选数组是 undefined；经 Action 执行同一函数时，它们会被传成空数组。
  • AIP Logic 的 token 与块切分。Logic 中的所有活动都计入 token 限制，包括工具返回。限制按块重置。建议只向模型暴露必要属性；必要时把一个大 Use LLM 块拆成多块（每块有自己的上下文窗口）；能用确定性块就不要用 LLM。默认 temperature 为 0。
  • 读时权限不会自动保护模型输出和编辑。Blocks 文档写明：行级 / 列级访问控制（包括 restricted views、对象安全策略、属性安全策略）会在 Query objects 把数据读进提示词时过滤；这些控制不会延伸到模型输出，也不会延伸到 Apply actions 组成的本体编辑。下游保护需要再配 marking 或基于分级的访问控制。
  • Live Preview 的权限与通知。Live Preview 里对象类型权限取决于仓库对底层数据源的权限。测试会发通知的函数时，收件人权限不会被强制执行，因此预览成功、作为 Action 使用时失败是可能的。
  • 逻辑文件的位置与执行模式。逻辑文件必须放在项目文件夹，不能放主文件夹。user-scoped 与 project-scoped 不仅决定权限，也决定谁能看日志；project-scoped 还要求资源已导入同一项目。
  • Ontology SQL 自身的限制（以免把它当成万能查询层）：只支持读，不支持 INSERT / UPDATE / DELETE；每条查询原则上只有一个 SELECT（外加可选的 DECLARE）；不能在同一条查询里混用对象和 dataset；结果最多截断为 10,000 行；查询执行超时 20 秒；目前仅用于 Object Storage v2。对象集可以作为输入（取决于前端应用），但不能直接作为查询输出。

9. 本课未核实的地方

  • 本课只依据 2026-11-21（UTC+8）读到的公开英文文档，没有在 Foundry 租户里实际创建仓库、发布函数或运行 AIP Logic，因此不保证某一具体版本号、控制台文案或权限开关与你所在环境完全一致。
  • 关于 AIP Logic 是否支持 staged writes：语言功能表将 AIP Logic 的 “Staged writes support [Beta]” 标为 No；Automate · Logic effects 又说明了「启用 staged writes 的逻辑函数」不再返回本体编辑列表、需要改走 Action effect。两处公开口径不一致。本课在第 5 节转述了 Automate 文档的操作含义，但不判断哪一页更新、也不把「AIP Logic 已正式支持 staged writes」写成定论。
  • 语言功能表本身注明并非所有语言支持全部特性，个别单元格也可能滞后于产品。若要做实施决策，应以所在租户文档和实际发布结果为准。
  • 本课没有把「Ontology 上的计算」单列为一种与 Functions、AIP Logic 并列的产品。文档里的计算，分别落在函数返回值、Workshop 派生列与聚合、Quiver 指标，以及 Ontology SQL 查询上。
